3. CONTROL DESIGN AND INTENDED RISK MITIGATION

Customer due diligence

Intended mitigation: Complete required business-customer onboarding and risk checks before enabling payment initiation. Restrict or defer access when required information or checks are incomplete. Keep a reviewable record of the decision and any subsequent refresh requirement.

Evidence needed: Applicable onboarding criteria, synthetic test cases, incomplete-information and exception paths, completion timestamps, reviewer or system attribution, and evidence that payment access remains blocked until required checks are complete. This file does not establish that these controls have been implemented.

Sanctions screening

Intended mitigation: Screen relevant payment parties before submission, route potential matches for authorized human review, and prevent release while a required screening outcome is missing or unresolved.

Illustrative observation: A fictional GB web sandbox path is described as invoking screening before simulated submission. The source event and test record are not attached, so this is not independently verifiable evidence.

Evidence needed: GB and US route coverage, web and API coverage, test scenarios and expected outcomes, screening configuration and list provenance, match handling, escalation and release controls, false-positive review, service-unavailable behavior, and reviewer sign-off.

Transaction monitoring

Intended mitigation: Identify activity that meets configured monitoring scenarios, generate a reviewable alert, assign it to an authorized reviewer, and retain disposition and escalation rationale.

Illustrative observation: A synthetic monitoring scenario is described as configured to generate a simulated alert. No alert or disposition artifact is attached; configuration alone does not demonstrate effective monitoring.

Evidence needed: Scenario rationale and coverage, representative synthetic alert examples, disposition and escalation steps, ownership, tuning and change history, service failure handling, and documented operating-effectiveness testing.

API authentication and authorization

Intended mitigation: Authenticate each approved business client, authorize access only to permitted operations and data, validate requests, and record security-relevant events. Apply appropriate abuse and rate controls based on approved design.

Evidence needed: API security design, client and permission inventory, positive and negative authorization tests, request-validation results, rate-control tests, audit/logging evidence, credential lifecycle controls, and handling of authentication or authorization service failure. No API tests are included here.

Third-party access and assurance

Intended mitigation: Limit processor access to approved purposes and least privilege; define security responsibilities, incident notification, subcontractor controls, and evidence-review rights; periodically review access and relevant assurance material.

Evidence needed: Verified processor identity and service scope, contract and responsibility mapping, access inventory and review, assurance evidence, incident and continuity arrangements, subcontractor details, and issue-remediation tracking. The processor name in the intake is fictional and no vendor materials are attached.

Fail-closed service handling

Intended mitigation: Do not submit a payment when a mandatory screening result is unavailable, incomplete, or invalid. Define bounded retry and recovery behavior, prevent duplicate submissions, alert an operator to persistent failures, and retain the decision trail.

Evidence needed: Timeout and outage scenarios, retry and queue behavior, duplicate/idempotency tests, recovery evidence, operational alert ownership, and proof that a payment cannot bypass required checks. No service-failure tests are included here.
